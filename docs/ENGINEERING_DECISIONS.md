# Engineering Decisions

Short records of the decisions that shape LedgerForge, with the alternatives considered.

### ED-1: Modular monolith, not microservices
**Decision:** one Spring Boot application with domain packages and one PostgreSQL database.
**Why:** a payment capture must update a wallet, a merchant payable, fee revenue, the intent, an
outbox event, an audit row and an idempotency record atomically. In one database that is a single
ACID transaction. Across services it would need sagas and compensations.
**Alternative:** split ledger and payments into services. That is reasonable at large scale, and the
package boundaries (all postings go through `LedgerService`) make a later split possible.

### ED-2: Integer minor units everywhere
**Decision:** `BIGINT` minor units in the database, `long` in Java, safe integers in TypeScript.
Fee math uses `BigInteger` intermediates with explicit rounding. The JSON parser rejects floats.
**Alternative:** `NUMERIC`/`BigDecimal`. That is also correct, but integers make "no fractional paise"
structural, and they are cheaper.

### ED-3: Double-entry ledger plus a balance projection
**Decision:** entries are the source of truth. `account_balances` is a projection updated in the same
transaction and verified by reconciliation.
**Alternatives:**
* a single `wallet.balance` column: no audit trail and no accounting guarantees;
* computing balances with `SUM` on every request: correct, but O(history) on the hot path and harder to lock.

### ED-4: Invariants enforced twice (application and database)
**Decision:** `LedgerValidationService` gives precise, user-facing errors. PostgreSQL triggers
(immutability, currency, a deferred balance check) make violations impossible even for raw SQL or
future bugs.
**Trade-off:** some duplicated logic, and triggers are less visible than Java. Both layers are tested.

### ED-5: Pessimistic locks in deterministic order, READ COMMITTED
**Decision:** `SELECT … FOR UPDATE` on balance rows in ascending id order, after the business row.
**Alternatives:**
* SERIALIZABLE isolation: needs retry loops around every operation;
* optimistic versioning alone: under contention it turns into retries and gives worse user experience.

Versions remain as a safety net. See [CONCURRENCY.md](CONCURRENCY.md).

### ED-6: Idempotency claimed inside the business transaction
**Decision:** `INSERT … ON CONFLICT DO NOTHING` in the same transaction. Concurrent duplicates block
on the unique index, and failures leave no record.
**Alternatives:**
* a separate "in-progress" record committed first: needs crash recovery for stuck rows;
* an in-memory map: not durable, not shared between instances.

### ED-7: Transactional outbox with polling plus `SKIP LOCKED`
**Decision:** events are written with the business change, and a scheduled dispatcher and delivery
worker poll PostgreSQL.
**Alternatives:**
* Kafka with Debezium change data capture: more infrastructure than a sandbox needs;
* sending HTTP inside the transaction: couples latency and can notify about rolled-back changes.

### ED-8: JWT access token in memory, opaque rotating refresh token in an HttpOnly cookie
**Decision:** short-lived HS256 JWT (stateless verification) plus a server-side refresh session with
rotation and reuse detection. Each request also checks that the session family is active, which costs
one indexed lookup, so logout is immediate.
**Alternatives:**
* tokens in localStorage: exposed to XSS;
* server sessions only: simpler, but the brief asks for JWT, and the hybrid shows the trade-offs.

### ED-9: Spring Boot 4.1 and Java 21
**Decision:** use the latest stable Spring Boot (4.1.2: Spring Framework 7, Spring Security 7,
Hibernate 7, Jackson 3) on Java 21 LTS. Virtual threads serve requests, and webhook delivery runs
on a virtual-thread executor.

### ED-10: Frontend library versions
**Decision:** React 19, Vite 7, TypeScript 5.9, React Router 7, Tailwind 4, TanStack Query 5, Zod 4,
Recharts 3, Vitest 3. Newer majors (Vite 8, TypeScript 7's native compiler, React Router 8) were
available but were days or weeks old, and lint and tooling support lagged. Mature majors were chosen
for build reliability. UI primitives follow the shadcn/ui approach: Radix components copied into
`components/ui` rather than generated by its CLI.

### ED-11: CQRS-lite read models
**Decision:** writes go through JPA entities. Lists, statements and dashboards are hand-written SQL
(`JdbcTemplate`) that filters, aggregates and paginates in PostgreSQL.
**Why:** ledger read queries (net amount per viewer, window functions, `generate_series`) are clearer
and faster in SQL than in JPQL or in-memory code.

### ED-12: Cumulative fee rounding for refunds
See [LEDGER_DESIGN.md §4](LEDGER_DESIGN.md#4-partial-refunds-and-fee-rounding). Any refund sequence
reconciles to the paisa, and this is property-tested.

### ED-13: Insufficient funds keeps the intent confirmable; a processor decline fails it
**Decision:** an insufficient balance rolls back the confirm, so the intent stays `CREATED` and the
customer can top up and retry. A sandbox processor decline is a committed outcome (`FAILED`,
`payment.failed` event) because it is a real result, not a transient condition.

### ED-14: Refunds require merchant funds
**Decision:** a refund debits the merchant payable, which cannot go negative. Once the funds have
been paid out, refunds fail with `MERCHANT_INSUFFICIENT_BALANCE`.
**Alternative:** allow negative merchant balances (a merchant debt). That is more realistic, but it
needs collections logic that is out of scope.

### ED-15: Redis is not used
Rate limiting is in-process (token bucket). Nothing else needed a cache. Redis would be the first
addition for multi-instance rate limiting. The app runs without it, as the brief requires.

### ED-16: No fake features
Password reset, email verification and MFA are not implemented, so they do not appear in the UI.
Every dashboard figure comes from the API. Empty states are shown for new accounts.
